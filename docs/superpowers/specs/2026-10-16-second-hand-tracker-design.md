# Трекер завозів у секонд-хендах — дизайн

Дата: 2026-10-16
Статус: затверджено до планування

## 1. Задача

Людина регулярно ходить по секонд-хендах. Магазинів багато, і важко тримати в
голові, де коли завіз і до якої години магазин працює. Графіки завозів
періодичні («кожні 2 тижні в середу», «щотижня в понеділок»), але на практиці
порушуються.

Апка має відповідати на одне питання: **куди варто піти найближчими днями**.

### Для кого

Автор і коло друзів — 5–20 людей, закрита група. Усі бачать спільну базу і всі
можуть її наповнювати. Публічного доступу й реєстрації немає.

### Критерії успіху

1. Відкривши апку на телефоні, видно впорядкований список: де завіз сьогодні,
   завтра, через N днів — і чи магазин відкритий *зараз*.
2. Відмітити «завіз був» стоячи в магазині — два тапи.
3. Видно, наскільки даним можна вірити: коли останнє підтвердження і чи правило
   збігається з реальністю.
4. Друг заходить за посиланням, логіниться своїм email без пароля і відразу
   бачить ті самі дані.

### Чого ця версія не робить

Нагадувань і пушів, карти, фото, рейтингів магазинів, коментарів, публічної
реєстрації, модерації правок. Координати зберігаються, але використовуються
лише для показу відстані, якщо браузер дав геолокацію.

## 2. Технологічний вибір

Next.js (App Router) + TypeScript + Supabase (Postgres, Auth, RLS), деплой на
Vercel.

Розглянуті альтернативи:

- **Vite SPA + Supabase** — легша збірка, але серверна логіка (майбутній cron для
  нагадувань) потребувала б окремого бекенду.
- **Node + SQLite на власному VPS** — нуль зовнішніх залежностей і авторизація
  через спільний інвайт-код, але деплой, бекапи й сесії пишемо самі.

Обрано перший варіант: для цього масштабу — найменше коду на одиницю
результату, і шлях до нагадувань чи публічного режиму не вимагає переписування.

## 3. Модель даних

Часова зона фіксована в конфізі: `Europe/Kyiv`. Дати завозів зберігаються як
`date` без часу.

### `profiles`

| поле | тип | нотатка |
|---|---|---|
| `id` | uuid PK | = `auth.users.id` |
| `display_name` | text | ім'я для показу в журналі |
| `created_at` | timestamptz | |

### `allowed_emails`

Білий список доступу. Наповнюється вручну автором.

| поле | тип |
|---|---|
| `email` | text PK |
| `added_at` | timestamptz |

### `stores`

| поле | тип | нотатка |
|---|---|---|
| `id` | uuid PK | |
| `name` | text NOT NULL | |
| `address` | text | |
| `lat`, `lng` | double precision NULL | для відстані; необов'язкові |
| `notes` | text | «дорогий, але буває вінтаж» |
| `created_by` | uuid FK → profiles | визначає право видалення |
| `created_at`, `updated_at` | timestamptz | |

### `opening_hours`

Рядок на день тижня. Окрема таблиця (не JSON), щоб «що відкрито зараз» був
звичайним SQL-запитом.

| поле | тип | нотатка |
|---|---|---|
| `id` | uuid PK | |
| `store_id` | uuid FK → stores ON DELETE CASCADE | |
| `weekday` | smallint 0–6 | 0 = понеділок |
| `opens`, `closes` | time NULL | NULL якщо `is_closed` |
| `is_closed` | boolean NOT NULL DEFAULT false | |

Унікальність: `(store_id, weekday)`.

Якщо `closes < opens`, інтервал вважається таким, що переходить за полуніч.

### `delivery_rules`

Правило завозу. У магазину може бути кілька активних правил (бувають завози
двічі на тиждень різними днями).

| поле | тип | нотатка |
|---|---|---|
| `id` | uuid PK | |
| `store_id` | uuid FK → stores ON DELETE CASCADE | |
| `kind` | enum | `weekly`, `every_n_weeks`, `monthly_nth`, `irregular` |
| `weekday` | smallint 0–6 NULL | 0 = понеділок, як в `opening_hours`; потрібне для всіх, крім `irregular` |
| `interval_weeks` | smallint NULL | лише `every_n_weeks`, ≥ 2 |
| `anchor_date` | date NULL | лише `every_n_weeks`: дата відомого завозу, задає фазу |
| `nth` | smallint NULL | лише `monthly_nth`: 1–4, або -1 = останній |
| `time_of_day` | time NULL | «завозять зранку» — лише підказка, не впливає на розрахунок |
| `note` | text | |
| `is_active` | boolean NOT NULL DEFAULT true | вимкнути старе правило, не чіпаючи історію |
| `created_by` | uuid FK → profiles | |
| `created_at` | timestamptz | |

Обмеження на рівні БД: `every_n_weeks` вимагає `interval_weeks` і `anchor_date`;
`monthly_nth` вимагає `nth`; `irregular` вимагає `weekday IS NULL`.

### `delivery_events`

Журнал фактів — джерело живості даних.

| поле | тип | нотатка |
|---|---|---|
| `id` | uuid PK | |
| `store_id` | uuid FK → stores ON DELETE CASCADE | |
| `date` | date NOT NULL | |
| `happened` | boolean NOT NULL | true = завіз був; false = перевірив, завозу не було |
| `reported_by` | uuid FK → profiles | |
| `note` | text | «багато взуття» |
| `created_at` | timestamptz | |

Унікальність: `(store_id, date, reported_by)` — двоє можуть підтвердити
незалежно, одна людина не дублює себе.

## 4. Логіка прогнозу й довіри

Чистий модуль `lib/schedule/`, без React і без звернень до БД.

### Наступні входження

`nextOccurrences(rule, from, count) → Date[]`

- `weekly` — найближчий `weekday` від `from`, далі з кроком 7 днів.
- `every_n_weeks` — від `anchor_date` з кроком `interval_weeks * 7` днів;
  беруться дати ≥ `from`. Якір задає, *яка саме* середа з двох.
- `monthly_nth` — n-й вказаний день тижня в кожному місяці; `-1` = останній.
- `irregular` — порожній результат; прогноз для таких магазинів будується з
  журналу (медіанний інтервал між останніми 5 фактами, якщо їх ≥ 3; інакше
  прогнозу немає).

### Оцінка довіри

`confidence(rule, events, today)`:

- **Збіг правила:** для останніх 5 прогнозованих дат перевіряємо, чи є в журналі
  `happened = true` у вікні ±1 день. Результат — «збіглося K з N».
- **Свіжість:** днів з останнього будь-якого запису журналу для цього магазину.
- Прапорець `stale`, якщо свіжість перевищує подвоєний період правила
  (для `irregular` — 30 днів).

Ці два числа показуються в UI; апка не ховає розбіжність і не «виправляє»
правило автоматично.

### Години роботи

Окремий чистий модуль `lib/opening-hours/`: `isOpenAt(hours, instant)` і
`closesAt(hours, instant)`, з коректною обробкою інтервалів через полуніч.

## 5. Екрани

**Сьогодні** (головний). Магазини, впорядковані за близькістю наступного завозу:
«ЗАВІЗ СЬОГОДНІ» → «завтра» → «через N днів». Рядок: назва, відкрито/закрито
зараз, правило дрібним шрифтом, прапорець застарілості, відстань якщо є
геолокація.

**Магазин.** Години роботи на тиждень, активні правила, останні 10 записів
журналу. Дві основні кнопки: «Завіз був» / «Завозу не було», дата за
замовчуванням — сьогодні. Це головна дія апки. Нижче — «Редагувати».

**Усі магазини.** Список із пошуком по назві й адресі, кнопка «+ Додати».

**Форма магазину.** Назва, адреса, години роботи, правила. Одна форма і на
створення, і на редагування.

## 6. Архітектура й потік даних

```
app/                 екрани (Server Components, тонкі)
lib/schedule/        прогноз + довіра (чистий, без React і БД)
lib/opening-hours/   «чи відкрито зараз» (чистий)
lib/db/              запити до Supabase, файл на сутність
```

Компоненти не викликають Supabase напряму — лише через `lib/db/`.

Читання: Server Components на сервері при рендері. Запис (відмітка завозу,
редагування магазину): Server Action → запис → `revalidate` відповідного шляху.
Клієнтського стор-менеджменту немає.

## 7. Доступ

Supabase Auth, magic-link на email — без паролів.

RLS-політики:

- `stores`, `opening_hours`, `delivery_rules`, `delivery_events`: читання й
  вставка — будь-який залогінений користувач, чий email є в `allowed_emails`.
- Оновлення `stores`, `opening_hours`, `delivery_rules` — будь-який такий
  користувач (спільне наповнення й виправлення).
- Видалення `stores` — тільки `created_by`.
- Видалення `delivery_events` — тільки `reported_by`.
- `allowed_emails` — читання заборонене клієнту, правиться лише через консоль
  Supabase.

Конфлікти одночасних правок не розв'язуються (last-write-wins) — для групи
такого розміру це прийнятно.

## 8. Обробка помилок

Три випадки, що реально трапляться:

1. **Немає інтернету.** Показуються останні отримані дані з банером «дані можуть
   бути несвіжі».
2. **Запис не вдався.** Кнопка не «проглочує» тап: показується помилка, дія
   лишається доступною для повтору.
3. **Email не в білому списку.** Чесний екран «попроси доступ», не поломаний
   рендер і не нескінченний редирект.

## 9. Тестування

Розробка за TDD: спочатку тест на поведінку, потім реалізація.

**Vitest, модульні** — основне покриття, на чистих модулях:

- `every_n_weeks` через зміну місяця й через кінець року.
- `every_n_weeks` із якорем у майбутньому і в далекому минулому.
- `monthly_nth` для `nth = 1..4` і `-1`, включно з місяцями, де 5 таких днів.
- `weekly`, коли `from` — сам день завозу (входження = сьогодні, не наступний тиждень).
- `irregular` з 0, 2 і 5 фактами в журналі.
- `confidence`: ідеальний збіг, повний розбіг, збіг зі зсувом ±1 день.
- `isOpenAt`: магазин до 00:00, інтервал через полуніч, вихідний, межі хвилини.
- Перехід на зимовий і літній час у `Europe/Kyiv`.

**Playwright, e2e** — один сценарій: зайти → додати магазин із правилом
«кожні 2 тижні, середа» → відмітити завіз → побачити його на головному екрані.

## 10. Подальші фази (не зараз)

Нагадування (web-push або Telegram-бот + cron), карта з маршрутом по кількох
точках, фото знахідок, публічний режим із модерацією.
